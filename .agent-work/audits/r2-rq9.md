## A. Path smoothing (RQ8)

**Where.** ares only passes `smoothing: bool = False` through: `managers/path_manager.py:257` (param), `:275-277` (doc: "nodes are removed if it's possible to jump ahead some tiles in a straight line with a lower cost"), `:335` (`map_data.pathfind(..., sensitivity=sensitivity, smoothing=smoothing)`). Exposed on PathUnitToTarget (`behaviors/combat/individual/path_unit_to_target.py:56,72`), PathGroupToTarget (`.../group/path_group_to_target.py:70,97`), MoveToSafeTarget (`.../move_to_safe_target.py:65,86`), NydusPathUnitToTarget. `find_low_priority_path` and `raw_pathfind` never smooth.

**The algorithm is not in ares, but it is public.** It is in map_analyzer's C extension, `extension/ma_ext.c`, function `create_smoothed_path` (called by exported `astar` and `astar_with_nydus` when `smoothing != 0 && path_length >= 3`). `MapData.pathfind(start, goal, grid=None, large=False, smoothing=False, sensitivity=1)` delegates to `Pather.pathfind` (not read; its docstring says sensitivity = `path[::sensitivity]` on the returned path, i.e. after smoothing). Behaviour as read from the C source (a summarised read, not verbatim; re-read the file before writing the ticket):
1. Walk the full A* node list start to goal, keeping `segment_total_weight` (running cost of the original path since the last kept node) and the last kept node.
2. For each next node: `segment_total_weight += weights[next] * octile_distance(current, next)`.
3. `line = calculate_line_weight(last_kept, next)`. That samples the straight line at 5 samples per cell (`dots = 5 * (int)flight_distance`), truncates each to a cell, dedupes cells, sums their weights (early exit at `HUGE_VALF`), multiplies by `flight_distance / sample_count`. No explicit blocked check: blocked cells carry `HUGE_VALF`, so the sum explodes and the shortcut is rejected.
4. If `line > segment_total_weight * 1.002` the straight line is worse than the path: keep the current node as a waypoint and reset the segment weight to the last step's weight. Otherwise skip the node.
5. Always append the goal. Tolerance 1.002 and 5 samples/cell are hard-coded; `smoothing` is an on/off flag.

**What core has.** `resources/pathing.ts`: `pathIndices` (`:83-91`) runs `createAStar` (`utils/pathing/astar.ts`: 8-neighbour, octile heuristic, cost = `data[next] * step`, same cost model as the ext). `findPath` thins by `sensitivity` (`:123-129`); `nextPoint` returns `path[min(max(1, sensitivity), len) - 1]` (`:158`). Consumers: `behaviors/combat/group.ts:65-136`, individual `pathUnitToTarget`. P5-D12 (parity-5.design.md:287) dropped `smoothing`; parity-r2.md RQ8 recommends keep dropped.

**Porting concretely.** Pure function `smoothPath(path: Int32Array, data: Float32Array, width): Int32Array` in `utils/pathing/smooth.ts` (next to `astar.ts`), implementing steps 1-5 (octile step cost as in astar's `visit`). Add `smoothing?: boolean` to `findPath`/`nextPoint` options and to pathUnitToTarget, pathGroupToTarget, moveToSafeTarget; apply in `pathIndices` consumers before sensitivity thinning. Tests: straight corridor collapses to start+goal; path around an Infinity block keeps the corner nodes; influence-blob detour is kept; `< 3` nodes untouched.

**Caveat.** Exact node-for-node parity needs the same sampling quirks (end cell not guaranteed sampled, 5 samples/cell, the `norm` factor). A looser Bresenham line-of-sight string pull is a cousin, not identical. Nydus variant is out (Zerg, RQ1).

**Size** S (~80 lines + tests). **Level** senior-lite: small, but tolerance and sampling must be matched against the C source; a junior can do it with the step list above and the C file open. **Portable** yes. **Worth it** low: default off in ares, and `sensitivity` already thins waypoints.

## B. Adept shade tracking

**ares (main.py).**
- State (`:129-132`): `adept_shades: defaultdict[int, dict]` (shade tag to `{SHADE_OWNER, SHADE_COMMENCED}`), `adept_tags_with_shades_assigned: set[int]`. Constants `consts.py:119` `ADD_SHADES_ON_FRAME = 120`, `:129` `SHADE_DURATION = 160`.
- `_should_add_unit` (`:866-889`), called for enemies only in `_prepare_units` (`:274-275`): for an `ADEPTPHASESHIFT`, record on first sight, return `game_loop - commenced >= 120`. Other units: True. If False the shade is skipped entirely (not in `all_units`/enemy caches, never reaches grids, memory or enemy lists).
- `_record_shade` (`:763-799`): on first sight, find enemy ground units within 40 (`unit_memory_manager.units_in_range(..., EnemyGround)`) that are ADEPTs without an assigned shade; if any, owner = closest to the shade, commenced = now, mark owner assigned (it marks `close_adepts.first.tag`, not the closest: minor ares bug); else owner 0 and commenced = `now - 32` ("assume 20% complete"). So a shade becomes visible 120 frames after first sight (88 with no owner).
- `_clear_adept_shades` (`:738-761`, each step `:214`): drop entries where `game_loop - commenced > 160`, release the owner tag.
- Intent: a shade is harmless until the adept teleports to it, so only treat it as a unit near completion.

**core today.** No shade logic. `constants/influence.ts:27` gives `ADEPTPHASESHIFT` `{groundCost: 9, groundRange: 5}` and `resources/influence.ts:105-112` stamps it (range + `rangeBuffer` 4) for every enemy in `memory.getEnemies()` for the whole shade life, so the ground grid and avoidance flee a shade that can't hurt anything for most of its life. Per-unit first-seen is not tracked (`engine/create-unit.ts:92` only has `lastSeen`).

**Porting concretely.** Simplest faithful version, in the `resources/influence.ts` enemy loop: skip `ADEPTPHASESHIFT` until `gameLoop - firstSeenLoop >= 120`. Needs `shadeFirstSeen: Map<tag, loop>`, pruned after 160 (+margin) during the same rebuild; skip the owner assignment (only affects ares' later resync, with a -32 fallback anyway). Alternative that removes tracking: raw `Unit.buff_duration_remain` / `buff_duration_max` (raw.proto:150-151, "how long a buff or unit is still around (eg mule, broodling)"; core types `buffDuration*` in `types.ts`). Skip the shade while `remain/max > 1 - 120/160`. Needs one live check that the field is populated for enemy shades; if it is, it beats frame counting (survives vision loss). ares hides the shade everywhere; core would hide it only from influence unless `memory` is also touched (decide in the ticket).

**Size** S (~30 lines + test). **Level** junior: one loop, one map, unit test with fake enemies at loops 0, 119, 120; the buff-duration variant needs the live check, give that part to a senior. **Portable** yes. **Value** real but narrow (Protoss opponents with adepts).

## C. Ability tracker

**Verdict.** Don't port: dead in ares, superseded by the query. Only plausible consumer: a bot that sets `skipAvailableAbilitiesQuery` for speed and wants frame cooldowns for a few abilities. If ever wanted: a resource with `track(unit, ability)`, `used(unit, ability)`, `ready(unit, ability)`, table in `constants/dicts/ability-cooldown.ts`, using `GAME_LOOPS_PER_SECOND` not 22.4; M, junior. No raw-API cooldown field exists for abilities, so frame tracking is the only route.

## D. ENEMY_NAT_HG_SPOT

**ares.** Build step target (`consts.py:229`). Two resolvers:
- `build_runner/build_order_runner.py:762-770` (live runner): `mediator.get_closest_overlord_spot(from_pos = towards(enemy_nat, map_center, 10.0))`.
- `build_runner/build_order_parser.py:682-683`: `mediator.get_ol_spot_near_enemy_nat` (cached property, `managers/terrain_manager.py:319-333`), same anchor.
- `terrain_manager.get_closest_overlord_spot` (`:374-399`): nearest of `ol_spots` by Euclidean distance (initial 999.9, falls back to `map_center` if none), then **pops that spot from the cached list**, so a second request gets the next-nearest. `ol_spots` (`:307-316`) = `map_data.overlord_spots`.
- Use: overlord scout waypoint ("HG" = high ground, where the overlord is out of ground reach).

**Where spots come from.** `MapData.__init__`: `self.overlord_spots = self.c_ext_map.overlord_spots`, computed in the map_analyzer C ext (`CMapInfo(pathing_grid.T, terrain_height.T, playable_area, map_name)`). I did not read the selection rules in `ma_ext.c`; unknown.

**core.** `parse.ts:60` throws `NodeSC2Error` for it; `utils/build-order/targets.ts` has `ENEMY_NAT_VISION` (distance 10 toward map centre, same anchor). Overlord spots deferred in 6a (parity-6b.design.md:59,306); core has no overlord-spot concept (grep).

**Porting.** (1) the resolver (anchor + nearest + pop): trivial once spots exist. (2) the spot list: must be reimplemented from `ma_ext.c` using the map pathing and terrain-height grids (`resources/map.ts`, `utils/map/*`). L, senior (reverse-engineer from C, validate on fixture maps). **Portable** in principle (public C over public grids) but all the cost is the generator, and overlord spots serve Zerg play (RQ1, Zerg out of scope). **Verdict: do not port**; keep the NodeSC2Error.

## E. Protoss supply -1

## F. Shipped protoss_building_placements.yml

**File.** `protoss_building_placements.yml` at the ares package root, 816 lines, header `# 2025 patch 5.0.14`. 7 maps: Incorporeal, Persephone, Pylon, Torches, LeyLines, Ultralove, Magannatha. **How ares uses it.** Loaded as the *internal default* for Protoss: `ConfigParser(ares_dir, user_dir, f"{race}_building_placements.yml")` (`placement_manager.py:154-162`, `consts.py:27`). `config_parser.py:46-95`: internal parsed, optional user file from the bot's cwd, recursive dict merge where **leaf lists are replaced by the user's**. `UserPlacementExtractor` (`user_placement_extractor.py:13-150`): `normalize_map_name` lowercases and strips a trailing `le`/`aie` (with or without a space) and spaces; spawn Upper if `start.y > enemy_start.y`; `VsRandom` when race unknown; `VsAll` merged into the race block without overriding (lists appended, deduped); `iter_point_pairs` accepts `[x,y]`, nested lists, mixtures. `placement_manager._apply_user_building_location_info` (`:513-720`): validates each spot with `can_place_structure` and the avoid grid (bad spots warn and skip); key mapping: `PylonsWall` 2x2 wall + production_pylon, `ThreeByThreesWall` 3x3 wall, `StaticDefencesWall` 2x2 static_defence + wall, `*ReaperWall` reaper_wall, `FirstPylon` 2x2 wall + first_pylon (also a 16x16 avoid area, `:704-710`), `GateKeeper` into `_gatekeeper_positions[closest base]` (a unit hold spot). Each spot attaches to the closest expansion at equal terrain height (`:714-720`).

**core.** `examples/ares/custom-building-placements.ts`: `PlacementTable` (`:15-24`), `KEY_SPOTS` (`:28-41`, no FirstPylon/GateKeeper/ReaperWall), one-map `PROTOSS_PLACEMENTS` (Persephone, `:171-195`), `resolvePlacements` (`:197-222`: **matches map by `gameMapName.startsWith(name)`, not ares' normalisation**; spawn pick and VsAll merge like ares), `createPlacer` (`:240`). Hook: `Placer.placements?` (`types.ts:1234`), `placement.add` (`:1023`), `UserPlacement` (`:1008`). T16 plan: `parseAresPlacements` + `createPlacer` moved to `utils/placement/placer.ts` (parity-r2.md:486-505, design C10 `parity-r2.design.md:156-165`); C11 adds `firstPylon` and `gateKeeper`.

**Loading the data.** `Bun.YAML.parse` reads it as-is. Beyond T16's text: (a) use ares' map-name normalisation, not `startsWith` (`startsWith('Pylon')` matches any map starting "Pylon"; `LeyLines` never matches "Ley Lines AIE"); (b) Reaper-wall, FirstPylon, GateKeeper keys must map to core flags or warn; (c) leaf-list replacement if core wants ares-style layering over defaults; (d) confirm `placement.add` rejects invalid spots like ares' validation.

**Ship it in core?** Recommend no: coordinates are tied to 2025 map revisions (patch 5.0.14) and go stale; ares loads it implicitly while core has no default-resource mechanism and is race-neutral; the user's bot is Terran, nothing consumes it. MIT licence (ares `LICENSE`) allows copying. Use as a test fixture (T16 acceptance already says so), optionally also under `examples/ares/data/`. **Size** S on top of T16. **Level** junior (spec exists), flag the normalisation fix explicitly.
